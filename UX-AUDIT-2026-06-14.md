# UX/UI Audit — Web-native Geoprocessing Suite

**Date:** 2026-06-14
**Auditor:** Emma (design analysis)
**Scope:** Current UI state, problems, design direction, phased recommendations

---

## 1. Current State Summary

The app is a functional browser-based GIS workbench with:
- **4-pane layout:** left rail (artifacts), center (MapLibre map), right panel (details/history), bottom dock (5 tabs)
- **13 spatial operations** exposed as toolbar buttons (buffer, centroid, convex hull, envelope, simplify, dissolve, area, perimeter, compactness, reproject, clip, intersect, attribute join)
- **3 input methods:** direct SQL, natural language ("Ask"), data discovery ("Discover")
- **Rich provenance tracking:** CRS metadata, warnings, lineage, display transforms
- **Dark theme** with a consistent but utilitarian visual language

**App.tsx is 2,800+ lines.** The component is a monolith — all state, all dialogs, all logic in one file. This is an architectural debt that compounds every UX problem below.

---

## 2. The 5 Most Impactful UX Problems

### Problem 1: The Toolbar Explosion

**What:** 13 operation buttons sit in the top bar, all visible simultaneously when a spatial artifact is selected. They're flat, same-weight, text-only `<button className="secondary">` elements with no grouping, icons, or visual hierarchy.

**Why it hurts:**
- A new user sees "Buffer", "Centroid", "Convex Hull", "Envelope", "Simplify", "Grouped Dissolve", "Area", "Perimeter", "Compactness", "Reproject", "Clip", "Intersect", "Attribute Join" — all equally weighted, no guidance on which to use or in what order
- No grouping by category (geometry transforms vs. measurements vs. topology vs. joins)
- No icons or visual differentiation — it's a wall of text buttons
- The toolbar grows linearly with each new operation — it doesn't scale
- Operations that need two inputs (clip, intersect, attribute join) look identical to single-input operations

**Impact:** ★★★★★ — This is the primary "unfriendly" feeling. It assumes the user already knows GIS.

---

### Problem 2: No Onboarding / Empty State

**What:** A new user opens the app and sees: a blank map centered on San Francisco, a left rail saying "No project artifacts yet. Import data to begin.", and a top bar with "New / Save Project / Open Project / Load sample / Import".

**Why it hurts:**
- No guided first action — the user must independently decide to click "Import" or "Load sample"
- No visual cue that "Load sample" is the fastest path to seeing the app work
- The map is blank and lifeless — it doesn't communicate what the tool does
- The bottom dock shows "Table" tab with "Select or import a spatial artifact to inspect rows" — passive, not inviting
- A user who doesn't know what GeoJSON or GeoParquet is has no path forward

**Impact:** ★★★★★ — The 30-second first-task goal is not met. Most users would bounce.

---

### Problem 3: Bottom Dock Cognitive Overload

**What:** The bottom dock has 5 tabs: Table, SQL, Results, Ask, Discover. Each has a completely different interaction model:
- **Table:** data grid with row selection synced to map
- **SQL:** freeform text editor with run button
- **Results:** query preview with materialize flow
- **Ask:** natural language input with candidate matching and plan execution
- **Discover:** external data search with geocoding and bbox confirmation

**Why it hurts:**
- 5 tabs is too many for a panel that occupies ~260px of vertical space
- Each tab has different mental model and interaction pattern
- "Results" only has content after running a SQL query — it's often empty
- "Ask" and "Discover" are conceptually different from "Table/SQL/Results" but live in the same dock
- The user has to tab-switch constantly to move between inspection (Table), query (SQL), and results
- No visual connection between "I wrote SQL" → "here are results" → "here's the table"

**Impact:** ★★★★☆ — The bottom third of the screen is confusing and underutilized.

---

### Problem 4: Dialog Proliferation for Operations

**What:** Each spatial operation opens a modal overlay dialog. There are 13+ dialog variants, many sharing the same structure (source summary → contract display → warnings → output semantics → name input → run button). The buffer dialog alone is ~80 lines of JSX.

**Why it hurts:**
- Every operation interrupts the user with a full overlay that blocks the map
- The dialogs are verbose — they show "contract displays", "output semantics", "geometry support" tables, and CRS warnings before the user can even name the output
- A user who just wants to buffer their parcels by 1km must read through 4-5 informational cards before finding the distance input
- The dialogs don't share a consistent component — each is hand-written inline in App.tsx
- No way to quickly re-run an operation with different parameters

**Impact:** ★★★★☆ — Operations feel heavy and bureaucratic instead of fluid.

---

### Problem 5: Information Architecture Mismatch

**What:** The left rail shows "Project / Data" → artifacts list → saved queries. The right panel shows "Details / History" with artifact metadata, lineage, warnings, and history events. The bottom dock shows data inspection and query tools.

**Why it hurts:**
- The user's mental model is: "I have data → I do things to it → I see results." The UI splits this across 4 zones with no clear flow
- "Saved Queries" in the left rail is a secondary feature that takes up valuable space
- The right panel mixes artifact details (metadata, CRS, warnings) with project history (event log) — these are different concerns
- Warning badges appear in 3 places: left rail (artifact cards), right panel (details), and dialog overlays — the user doesn't know where to look
- The "Details / History" right panel title doesn't communicate what it contains

**Impact:** ★★★☆☆ — The layout is functional but doesn't guide the user through a coherent workflow.

---

## 3. Design Direction

### Layout Philosophy: **Command Console + Living Map**

Instead of 4 equal-weight panes, restructure around two primary surfaces:

```
┌─────────────────────────────────────────────────────────┐
│  Top bar: project name · import · export · operations ▾ │
├──────────┬──────────────────────────────┬───────────────┤
│          │                              │               │
│  Layer   │         MAP                  │  Inspector    │
│  Panel   │         (primary)            │  (context-    │
│  (narrow)│                              │   sensitive)  │
│          │                              │               │
│          ├──────────────────────────────┤               │
│          │  Console (unified bottom)    │               │
│          │                              │               │
└──────────┴──────────────────────────────┴───────────────┘
```

**Key shifts:**
1. **Map is king.** It gets 60%+ of the viewport. It's the spatial anchor.
2. **Layer panel** (left) is narrow (~200px) — just artifact names, types, visibility toggles. No saved queries, no project management.
3. **Inspector** (right) is context-sensitive — shows whatever's selected: artifact metadata, operation results, feature details. Collapses when nothing's selected.
4. **Console** (bottom) is unified — a single panel with a mode switcher, not 5 disconnected tabs.

### Visual Language

**Principle: Earn every pixel.**

- **No badge walls.** Consolidate status indicators. One status line per artifact, not 5 badges.
- **Icons + text** for operations. Group by category with dividers.
- **Monospace for data, sans-serif for chrome.** Clear typographic hierarchy.
- **Accent color = action.** Blue for primary actions, amber for warnings, muted for everything else.
- **Depth through layering, not borders.** Use subtle elevation (shadows, opacity) instead of 1px borders on every card.

### Interaction Patterns

1. **Progressive disclosure:** Default view shows the essential. "Show more" reveals contract details, CRS metadata, provenance.
2. **Inline actions over dialogs:** Operations should appear as inline panels or sidebars, not full-screen overlays.
3. **Smart defaults:** Pre-fill operation parameters from context (e.g., buffer distance unit from CRS, output name from source + operation).
4. **Keyboard-first for power users:** Cmd+K command palette for operations, SQL focus, artifact switching.

**Goal:** Fix the most visible problems without restructuring.

│ │Buffer│ │Simpl│ │Area│ │Perm.│ │Clip│ │Attr.Join │ │
│ └─────┘ └─────┘ └────┘ └─────┘ └────┘ └─────────┘ │
│ ┌─────┐ ┌─────┐ ┌─────┐        ┌────────┐         │
│ │Centr│ │Hull │ │Envel│        │Intersect│         │
│ └─────┘ └─────┘ └─────┘        └────────┘         │
│ ┌──────────┐ ┌──────────┐                          │
│ │Dissolve  │ │Reproject │                          │
│ └──────────┘ └──────────┘                          │

- Add simple SVG icons (or Unicode symbols) to each button
- Use `<details>` or a dropdown menu per category instead of showing all 13 at once
- Only show operations that are valid for the selected artifact (hide polygon-only ops for point data)

#### 1b. Improve empty state
Replace the blank map + passive text with:

```
┌────────────────────────────────────────────────────┐
│                                                    │
│            🗺️  Web-native Geoprocessing            │
│                                                    │

│                                                    │
│     Supported: GeoJSON, GeoParquet                 │
│                                                    │
│     Tip: "Load sample" shows demo parcels          │
│     with all operations available.                 │
│                                                    │
└────────────────────────────────────────────────────┘
```

#### 1c. Streamline operation dialogs
For all operation dialogs:
- Move "Output semantics" and "Contract display" behind a "Show details" disclosure
- Put the **action inputs** (distance, grouping field, target CRS) at the top
- Put the **name input** last, pre-filled
- Reduce the dialog to: Source → Parameters → Name → Run

**Estimated effort:** ~4-6 hours of focused work. Touches CSS + some JSX restructuring but no architecture changes.

---

### Phase 2: Layout Restructure (3-5 days)

**Goal:** Implement the new pane layout.

#### 2a. Collapse App.tsx monolith
Extract into focused components:
- `OperationToolbar.tsx` — grouped operation launcher
- `OperationDialog.tsx` — single parameterized dialog component (replaces 13 inline dialogs)
- `ArtifactPanel.tsx` — left rail
- `InspectorPanel.tsx` — right panel
- `ConsolePanel.tsx` — unified bottom panel
- `MapPane.tsx` — map container + overlays

#### 2b. New grid layout
```css
.app-shell {
  grid-template-columns: 200px 1fr 280px;
  grid-template-rows: 48px 1fr 240px;
  /* Inspector collapses to 0 when nothing selected */
}
```

#### 2c. Unified console panel
Replace 5 tabs with 3 modes:
- **Inspect** (was Table) — data grid, row selection, feature inspection
- **Query** (was SQL + Results) — split view: SQL on left, results on right
- **Tools** (was Ask + Discover) — natural language + discovery combined

#### 2d. Context-sensitive inspector
Right panel shows:
- **No selection:** project overview, quick stats
- **Artifact selected:** metadata, CRS, warnings, lineage (collapsible sections)
- **Feature selected:** properties, geometry info
- **Operation result:** provenance, comparison with source

---

### Phase 3: Polish & Delight (1-2 weeks)

**Goal:** Make it beautiful and fluid.

#### 3a. Visual design system
- Define spacing scale (4px base)
- Define color tokens (not raw hex)
- Define typography scale
- Build reusable card, badge, button, input components
- Consistent hover/focus/active states

#### 3b. Command palette (Cmd+K)
- Fuzzy search for operations, artifacts, saved queries
- Keyboard shortcut display
- Recent actions

#### 3c. Map interactions
- Click feature → select in table + highlight in inspector
- Hover feature → tooltip with key properties
- Multi-select → batch operations
- Drawing tools for bbox/point selection

#### 3d. Drag-and-drop import
- Drop zone on the map
- File type detection
- Instant preview

#### 3e. Operation history as a visual timeline
- Replace the flat event list with a visual timeline
- Show operation → output relationships as a graph
- Allow clicking any node to inspect

## 5. Specific Wireframe: Redesigned Operation Flow

### Current flow (buffer example):
1. Select artifact
2. Click "Buffer" in toolbar
3. Full-screen overlay appears with: source summary, contract display, warnings, output semantics, distance input, name input
4. Read through 4-5 informational cards
5. Enter distance
6. Enter name
7. Click "Run Buffer"
8. Overlay closes, new artifact appears

### Proposed flow:
1. Select artifact
2. Press `Cmd+K` → type "buffer" → Enter (or click Operations → Transform → Buffer)
3. **Inline panel** slides in from right (replaces inspector):
   ```
   ┌─────────────────────────┐
   │ Buffer                  │
   │                         │
   │ Source: parcels         │
   │                         │
   │ Distance: [1    ] [km▾] │
   │                         │
   │ Name: [parcels_buffer]  │
   │                         │
   │ ▸ Show contract details │
   │                         │
   │ [Run Buffer]            │
   └─────────────────────────┘
   ```
4. Click "Run Buffer"
5. Panel shows result summary, artifact appears in layer panel

**Difference:** From 7 steps to 4. From a wall of text to a focused panel. From blocking overlay to side panel.

## 6. What NOT to Change

- **MapLibre integration** — it works, keep it
- **Spatial engine** — proven and stable
- **DuckDB-WASM integration** — solid foundation
- **Provenance model** — rich and well-designed
- **CRS handling** — thorough and correct
- **Data persistence** — works
- **NL query resolver** — good foundation, needs UX wrapper
- **Discovery panel** — good concept, needs integration polish

The engine is strong. The presentation is the problem.

## 8. Recommendation

**Start with Phase 1.** It's the highest ROI — grouping the toolbar, improving the empty state, and streamlining dialogs will transform the feel of the app without touching the architecture. You'll know immediately whether the direction is right.

Phase 2 is the structural investment that makes Phase 3 possible. Don't skip it, but don't start there either.

The app has excellent bones. The spatial engine, provenance model, and data flow are genuinely good. The UX problem is presentation, not capability. Fix the chrome, keep the engine.
